This file maps each claim in link:README.adoc[README.adoc] to the code that implements it,
the evidence that checks it and its limits, for anyone deciding how far to trust it.

[IMPORTANT]
====
zig-dnssec is experimental and has not been independently reviewed. Nothing below is
a substitute for that review.
====

== Claims and their implementation

=== Wire codec

[quote, README.adoc]
____
bounds-checked decoding that rejects malformed messages (compression pointers must point
strictly backwards; names in RDATA are decompressed only where RFC 3597 permits; trailing
data, misplaced OPT and meta-types are rejected), and an encoder with name compression.
____

How this is implemented::
link:src/wire/message.zig[], link:src/wire/name.zig[] and link:src/wire/rdata.zig[]. The
presentation format is in link:src/wire/text.zig[]. Each strict prefix of a valid message
is rejected by the unit tests, and the fuzz targets are described in
link:docs/reports/FUZZ-RESULTS.adoc[].

Caveat::
Tested and fuzzed, not proved. Fuzzing found and fixed one integer overflow in name
decoding.

=== Signatures

[quote, README.adoc]
____
RSASHA1, RSASHA1-NSEC3-SHA1, RSASHA256, RSASHA512, ECDSAP256SHA256, ECDSAP384SHA384 and
ED25519, all through Zig's standard library; DS digests SHA-1, SHA-256 and SHA-384. No
cryptographic primitive is implemented here.
____

How this is implemented::
link:src/dnssec/crypto.zig[] calls Zig's `std.crypto`. The tests are the RFC known-answer
vectors in link:tests/vectors.zig[].

Caveat::
The correctness of `std.crypto` is assumed, not reviewed here (see the proof ledger).

=== Chain of trust

[quote, README.adoc]
____
DS → DNSKEY → RRSIG from the signer up to the closest trust anchor, RRSIG validity windows
in RFC 1982 serial arithmetic, CNAME and DNAME chains, wildcard expansion.
____

How this is implemented::
The code is link:src/dnssec/validator.zig[], link:src/dnssec/rrset.zig[] and
link:src/dnssec/anchors.zig[]. It is checked by link:tests/replay.zig[], which replays 263
recorded responses, and by the Unbound and ldns cross-check
(link:tests/crosscheck/REPORT.adoc[]). The decision procedure is proved sound in
link:verification/proofs/agda/ChainOfTrust.agda[] and re-proved in Rocq and Lean (see the
proof ledger).

Caveat::
The proof is about a model of the chain walk. That `validator.zig` follows the model is
argued, not proved. Closest-anchor selection, validity windows and wildcards are tested,
not proved.

=== Denial of existence

[quote, README.adoc]
____
NSEC and NSEC3 proofs for NXDOMAIN, NODATA, wildcards and insecure delegations, including
Opt-Out and the RFC 6840 restrictions.
____

How this is implemented::
The code is link:src/dnssec/nsec.zig[] and link:src/dnssec/nsec3.zig[]. The tests,
link:tests/denial.zig[], cover every Appendix B example of RFC 4035 and RFC 5155.

Caveat::
Tested, not proved. The chain-of-trust proof treats a denial as one signed object and does
not model NSEC/NSEC3 semantics.

=== Verdicts that cannot be downgraded silently

[quote, README.adoc]
____
the result is `secure | insecure | bogus | indeterminate`. Answer data is reachable only
from the `secure` arm, or from the `insecure` arm together with the reason and the zone at
which insecurity was _proven_. Every failure is `bogus` or `indeterminate`.
____

How this is implemented::
In the library, the `Verdict` tagged union in link:src/dnssec/validator.zig[] carries an
answer only in the `secure` and `insecure` arms. At the C ABI, the Idris2 model in
link:src/interface/Abi/Types.idr[] makes an answer unrepresentable for Bogus and
Indeterminate. In the theory, the `fail-closed` theorem says a chain that is not fully
verified is `bogus`.

Caveat::
The Zig union is a type-level guarantee checked by the Zig compiler, not by a proof. The
theory covers the model, not the code.

=== Stub client

[quote, README.adoc]
____
DoH over TLS 1.2/1.3 with certificate verification, optional HTTP CONNECT proxy (TLS end to
end), RFC 8467 query padding.
____

How this is implemented::
link:src/stub/doh.zig[] and link:src/stub/client.zig[]. Every cross-check query goes
through this transport.

Caveat::
Zig 0.17.0's `std.http.Client` sends HTTPS requests in cleartext through a CONNECT proxy, so
the transport drives `std.crypto.tls.Client` itself. Correctness of the TLS client is
assumed.

=== From C, Idris2 and other languages

[quote, README.adoc]
____
The header is the contract: a verdict whose security is never `SECURE` unless the call
succeeded, and answer text only for `SECURE` and `INSECURE`.
____

How this is implemented::
The contract is link:src/interface/ffi/include/zig_dnssec.h[], implemented in
link:src/interface/ffi/src/main.zig[]. It is checked three ways:
+
* link:src/interface/ffi/test/abi_test.zig[] runs the C behaviour;
* link:src/interface/ffi/test/seam_test.zig[] compares the Idris2 model with the header;
* link:src/interface/E2e/Main.idr[] runs Idris2 → C → Zig end to end.

Caveat::
The Idris2 FFI marshalling and the library's memory safety are assumed (see the proof
ledger).

== Known gaps

[CAUTION]
====
Not implemented, as the README says: DNS-over-QUIC, Ed448 and GOST/SM2 signatures,
HTTP/2, RFC 5011 trust-anchor rollover, negative trust anchors, caching and QTYPE `ANY`.
What each gap means for a caller is in link:docs/architecture/THREAT-MODEL.adoc[].
====

[CAUTION]
====
Proofs stop at the model. That `validator.zig` follows the proved chain-of-trust
procedure is argued, not proved. Tracked in
link:https://github.com/hyperpolymath/zig-dnssec/issues/9[#9].
====

[CAUTION]
====
Independent review: none yet. Live validation against the real root was run by hand
once (2026-10-13) and is not automated.
====

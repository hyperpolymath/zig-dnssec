= zig-dnssec: what has been verified, and what has not
:toc:

Status as of 2026-10-13, Zig 0.17.0, Idris2 0.7.0. Every claim below is tagged with the
estate's five statuses and names the artefact that discharges it. The PROVEN rows are
about the C ABI seam (`src/interface/`) and are checked by Idris2; nothing about the
validator's own logic is proved yet.

[cols="1,4",options="header"]
|===
| Status | Meaning here
| PROVEN | discharged by a machine-checked proof (Idris2 typecheck of `src/interface/abi.ipkg`)
| TESTED | discharged by a test or run that is in the repository and reproducible
| ASSUMED | relied on without being checked here
| DESIGNED | built and reasoned about, but not exercised by a test
| OPEN | not done
|===

== Cross-check detail

263 queries (13 per leaf zone plus root, TLD, DNAME, Opt-Out and DS-at-non-cut
queries), run by `tests/crosscheck/run.sh`:

* *vs Unbound, default policy: 17 disagreements.* 12 are the Ed448 zone (we cannot
  verify Ed448: `bogus/unsupported_algorithm`; Unbound: secure) and 5 are negative
  answers from the zone with 200 NSEC3 iterations (`bogus/nsec3_iterations_exceeded`;
  Unbound: insecure). Both are deliberate default policies.
* *vs Unbound, RFC-permissive policy: 12 disagreements*, all Ed448 (ours: insecure).
* *vs ldns `drill -S`: 33 outcomes incompatible with ours.* 16 are the Ed448 and
  iteration cases. In the other 17 Unbound agrees with us and `drill -S` is coarser:
  nine NSEC/NSEC3 empty-non-terminal or wildcard-NODATA proofs it does not chase, three
  Opt-Out answers it reports as secure (RFC 5155 §9.2 says they are not), two DNAME
  answers it does not follow, one CNAME whose (tampered) target it does not validate,
  and two DNSKEY queries on the expired and not-yet-valid zones that it reports as
  successful.
* The first run found a real bug: a DNAME answer was rejected because the unsigned
  synthesised CNAME was examined before the DNAME. Fixed; DNAME is now processed first.

== The milestone-1 review cycle

Milestone 1 was reviewed externally before merge (`hyperpolymath/zig-dnssec`#4,
two automated review passes). Twelve findings were raised against
`src/dnssec/validator.zig`, `src/dnssec/rrset.zig`, `src/wire/name.zig`,
`src/wire/rdata.zig`, `src/stub/doh.zig` and `build/container/Containerfile`.
All twelve are fixed; the two that mattered most are described in
`docs/architecture/THREAT-MODEL.adoc` §"What the milestone-1 review found".

The test count went from 111 to 123 in that cycle, and to 126 in the second one
described below. The twelve additions from the first are:

* four unit tests in the sources they guard (`wire/name.zig` relative-name
  length overflow, `wire/rdata.zig` SVCB/HTTPS canonical form,
  `dnssec/rrset.zig` skew-bounded `effectiveTtl`, `stub/doh.zig` query
  component in the request target);
* seven replay tests in `tests/replay.zig`, built from the recorded
  cross-check fixtures by rewriting only fields an RRSIG does not cover — the
  question section, the received TTLs, and the presence and content of
  additional RRSIGs — plus one positive control that an anchored island below
  an insecure delegation validates as `secure`;
* one C ABI case in `src/interface/ffi/test/abi_test.zig` (`QTYPE=RRSIG` is
  refused with `ZIG_DNSSEC_ERR_INVALID_ARGUMENT`).

*Negative controls.* A regression test that passes on both the broken and the
fixed code proves nothing. Reverting `src/dnssec/validator.zig` and
`src/dnssec/rrset.zig` to their pre-fix state makes seven of the seven new
replay tests fail, each with the symptom its finding describes: a tampered
answer accepted as `insecure` under an island anchor; a forged NXDOMAIN
accepted as `insecure_delegation`; a valid chain broken by one extraneous DS
RRSIG; a valid wildcard answer rejected because of a forged `Labels` field; an
`insecure` answer cached for the attacker-chosen 86400 s; `QTYPE=CNAME` below
a DNAME returning `indeterminate`; and `QTYPE=RRSIG` returning `indeterminate`
rather than being refused. The positive control passed in both states, as it
should. The `wire/name.zig` test aborts the pre-fix build outright — the
overflow is a checked-arithmetic panic in Debug and ReleaseSafe, and an
out-of-bounds copy in an unchecked mode.

Two things this evidence does *not* establish. The fixtures are the 22 zones
of `tests/crosscheck/`, so a finding that needs a signed zone strictly below
an unsigned delegation cannot be built from them without new key material; the
island tests place the trust anchor below the insecure delegation instead,
which exercises the same code path with different key provenance. And no new
signed zone was generated for this cycle (`ldns-signzone` and `kskgen` were not
available), so every fixture is a recorded or minimally rewritten Unbound
response.

  Re-pointing the pin at today's parent tip and rewriting the path lists to
  make the gate green would certify convergence that has not been

== Estate note: what is proved, and where the next proof would go

The guarantee "answer data is only reachable with secure evidence or a proven-insecure
reason" is the kind of invariant the estate's epistemic-types work is meant to state: a
`secure` answer as knowledge, `insecure` as justified absence of authentication, and no
path from `bogus` to an answer. It is now stated as a type at the ABI seam
(`src/interface/Abi/`): an Idris2 caller cannot receive answer data with a bogus or
indeterminate verdict, even if the library wrote answer text for one (the FFI
marshalling and the library's memory safety are assumed). Inside the library the same
guarantee rests on the shape of a Zig tagged union and on tests. The next step towards
PROVEN is a model of the validator's decision procedure (the chain walk and the denial
proofs) in which "secure" can only be built from verified signatures up to an anchor;
that is a larger piece of work and is not started.

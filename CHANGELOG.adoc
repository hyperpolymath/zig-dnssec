=== [Unreleased]

==== Added

* DNS wire-format codec (RFC 1035): strict, bounds-checked decoding;
  encoding with name compression; presentation-format parser.
* DNSSEC signature verification through Zig's standard library: RSASHA1,
  RSASHA1-NSEC3-SHA1, RSASHA256, RSASHA512, ECDSAP256SHA256, ECDSAP384SHA384,
  ED25519; DS digests SHA-1, SHA-256, SHA-384.
* NSEC and NSEC3 denial-of-existence proofs (RFC 4035, RFC 5155, RFC 6840).
* Chain-of-trust validator with `secure | insecure | bogus | indeterminate`
  verdicts, static trust anchors (IANA root KSK-2017 and KSK-2024 built in),
  resource budgets, and fail-closed default policies.
* Validating stub client over DNS-over-HTTPS (HTTP/1.1, TLS end to end,
  optional CONNECT proxy) and the `dnssec-stub` command-line tool.
* Tests: RFC known-answer vectors, RFC appendix zones and responses, 263
  recorded responses replayed offline, mutation attacks, fuzz targets with a
  corpus; a cross-check against Unbound and ldns (`tests/crosscheck/`).
* `zig-ci` workflow; container image (`build/container/Containerfile`).
* C ABI (`zig build ffi`): `zig_dnssec.h` as the contract, a pure-Zig
  `libzig_dnssec` checked against it at compile time, and an Idris2 model of
  the interface (`src/interface/Abi/`) whose result type cannot carry an
  answer for a bogus or indeterminate verdict; tests keep the three in step,
  and an Idris2 end-to-end test (`just abi-e2e`) runs in CI.

==== Fixed

* Integer overflow in name decoding at the 255-octet boundary (found by
  fuzzing).
* DNAME answers were rejected because the synthesised CNAME was examined
  first (found by the Unbound cross-check).

Twelve findings from the external review of the milestone-1 pull request
(`hyperpolymath/zig-dnssec`#4, two automated reviews over `6d6a2b11` and
`4025364b`). Each has a regression test that was confirmed to fail against
the code it now guards; the two marked *security* accepted or produced
attacker-influenced data.

* *Security:* a forged RRSIG naming an insecure ancestor could bypass a
  closer trust anchor. Insecurity was inferred from the RRSIG's signer name
  alone, so an answer signed by a zone that is insecure from the root anchor
  was handed back as usable `insecure` data even when an anchor existed below
  that zone (RFC 4035 §5.2's closest-encloser rule). The signer is now
  rejected when a configured anchor is at or below it, and the answer is
  `bogus` (`bad_signer`).
* *Security:* the same defect on the denial path. `collectDenial` chose the
  zone from the first unauthenticated RRSIG signer and returned `insecure`
  before any signature over the NSEC/NSEC3/SOA records was checked. All
  candidate signers are now gathered deepest-first and the denial RRset is
  authenticated before it can establish anything.
* `computeZoneStatus` used only the first DS signature's signer; it now tries
  every signer of the DS RRset that is a strict ancestor of the child.
* An extra RRSIG over a DS RRset naming a different ancestor could break an
  otherwise valid chain (`no_matching_key` against the wrong keyset).
* A forged same-signer RRSIG with a smaller `Labels` field could change the
  depth at which a wildcard expansion was proved, rejecting valid answers.
  The `Labels` value now comes from the signature that actually verified, not
  from the minimum over all signatures present.
* An `insecure` answer could be cached for the TTL the responder chose: the
  received TTL of unsigned data is not signed, and the answer outlived the
  denial proof that made it acceptable. The proof's own TTL now bounds it.
* `QTYPE=RRSIG` was reported as `bogus` for a correctly signed response;
  nothing signs an RRSIG RRset, so it is now refused as `malformed_response`
  at the validator and `ZIG_DNSSEC_ERR_INVALID_ARGUMENT` at the C ABI.
* For `QTYPE=CNAME` below a DNAME, the synthesised CNAME *is* the answer
  (RFC 6672 §5.3.1); the validator redirected past it and then demanded a
  NODATA proof nobody is obliged to send.
* `effectiveTtl` wrapped to a huge value for signatures accepted only within
  the configured clock skew; it now measures to the widened window and fails
  closed at 0.
* The SVCB/HTTPS RDATA layout was missing, so the TargetName was hashed in
  the case it arrived in rather than canonical lowercase (RFC 4034 §6.2,
  RFC 9460 §2.2).
* A relative name joined to its `$ORIGIN` overflowed the `u8` length before
  the 255-octet check, panicking in safe modes and overrunning the name
  buffer otherwise.
* The DoH transport dropped the query component of a configured URI template,
  silently requesting a different endpoint (RFC 8484 §3.1).
* `build/container/Containerfile`: the `crosscheck` target's `CMD` chained
  `servers.sh stop` with `;`, so its exit status masked the cross-check's.

A second review cycle, over the merged milestone-1 tree, raised twelve more
findings. Eleven are fixed here; each is verified against the code as merged,
and the security ones carry a regression test that was confirmed to fail
without the fix (127 tests, up from 123).

* *Security:* an unsigned negative answer's SOA owner is unauthenticated data,
  and three paths used it to choose which zone got the insecurity check,
  guarded only by an ancestry test. Ancestry is not enough: with an anchor
  between the hinted zone and the target, the insecurity of an ancestor says
  nothing about the anchored subtree below it, so a forged SOA could dispose
  of a negative answer inside a secure island with no proof at all.
  `computeZoneStatus`, `nameStatus` and `proveDenial` now apply the same
  closest-anchor refusal the RRSIG signer check uses.
* *Security:* `usableDs` dropped SHA-1 when any stronger digest was present
  but left SHA-256 and SHA-384 both usable, so `keysFromDs` accepted
  whichever matched first and a child could be accepted through the weaker
  digest — the downgrade RFC 4509 §3 forbids, extended to SHA-384 by RFC 6605
  §5. Only the strongest supported digest class present is now kept.
* *Work amplification:* `readRr` sized every record's expansion buffer at
  `rdlen + 4 * 255`, including opaque types whose RDATA cannot grow at all.
  About 5,950 minimal 11-octet RRs fit in one 65535-octet message, so an
  untrusted upstream turned each message into ~6 MB of arena; `Session.fetch`
  caches every fetched message, so one validation at the default budget could
  hold hundreds of MB. The headroom now comes from the layout's actual name
  count (no supported layout has more than two), and is zero for opaque types.
* `dnssec-stub` exited 1 — the status it documents as "insecure" — for every
  setup and I/O failure, because an error escaping `main` becomes exit 1. A
  missing `--anchors` file, an unparseable trust anchor, a refused `http://`
  `--doh` URL, a bad `--ca` or an unwritable `--record` file each reported a
  proven-insecure verdict to any script or harness reading the status. Those
  are now mapped to the documented 4.
* `formatRr` emitted `(256-octet key)` for a DNSKEY and `(types)` for the
  NSEC/NSEC3 bitmaps. Neither is RDATA, and both the CLI and the C ABI promise
  presentation-format answer records. DNSKEY now emits base64 (RFC 4034 §2.2)
  and the bitmaps are enumerated as mnemonics; a key too large for the stack
  buffer falls back to RFC 3597 generic form for the whole RDATA.
* A `. DS` NODATA was always `bogus`/`denial_missing`: the strict-parent rule
  asks for a signer that is a proper ancestor of the target, and the root has
  none, so the root's own authenticated NSEC/SOA proof was discarded. At the
  root the signer can only be the root itself.
* A negative answer below a proven-insecure delegation was bounded only by the
  denial proof's lifetime, ignoring the SOA negative TTL, so a forged NXDOMAIN
  could be cached for the much longer DS/NSEC lifetime (RFC 2308 §5). It is
  now also bounded by min(SOA record TTL, SOA MINIMUM), and by zero when the
  response supplies no cacheable SOA.
* `parseTtl` accumulated compound TTLs in plain `u64`, so a long enough
  sequence such as repeated `4294967295w` overflowed before the final range
  check: a panic in Debug and ReleaseSafe, and a wrapped, wrongly small TTL
  otherwise, from the public zone parser. Accumulation is checked and bails as
  soon as the sum cannot fit `u32`.
* `parseRrsigTime` accepted impossible calendar dates — every month ran to
  day 31 — and `daysFromCivil` normalised rather than failed, so
  `20230231000000` was encoded as a March timestamp. The day is now validated
  against the month and both century leap-year rules.
* `build.zig.zon` shipped only `build.zig`, `build.zig.zon` and `src`, so
  `zig build test` in a package fetched through the Zig package manager failed
  on missing sources: the `test` step was advertised but its inputs under
  `tests/` and `tests/testdata/` were excluded. `tests` is now in `.paths`.
* `just crg-grade` and `just crg-badge` could never run. `just` does not treat
  `$$` as an escape — it passes both octets to the shell, where `$$` is the PID
  — so `grade=$$(grep …)` was a bash syntax error and the recipes exited 2.
  They now use `$`, and read `docs/status/READINESS.adoc`, which is where this
  repo keeps its assessment; they previously read `READINESS.md`, which does
  not exist here, and so returned the fallback grade for the wrong reason. The
  same defect is in the upstream contractile copy.

Not fixed in this cycle, with reasons rather than silence: the deed's
`:parent-pin` / `:template-commit` names a commit that no longer exists in
`hyperpolymath/rsr-template-repo`, so `check-variant-drift.sh` cannot be run
at all (see `docs/reports/VERIFICATION.adoc`); base-image digest pinning and
the container build stages' user model are left to the estate-wide pinning
decision because no registry or container engine is reachable from here to
verify either; and the negative-cache-TTL bound above has no test, because no
recorded fixture has an SOA MINIMUM below its own denial proof's TTL, so the
bound never binds in the corpus.

==== Changed

* `scripts/validate-template.sh` now honours the repo deed's
  `(paths :removed …)` list, and builds the root `build.zig` when the
  variant contract has removed `src/interface/ffi/build.zig`. Previously it
  required paths this variant deliberately deleted and, under `set -e`,
  aborted on the first one without reporting the rest.
* `zig-dnssec_chora.deed`: the `(variant (paths …))` clause closed with one
  parenthesis too many, which ended `(repo-deed …)` early and left
  `(provenance)` a sibling of it rather than a clause of it. No reader could
  reach the provenance facts — `scripts/deed-field.sh --has … provenance`
  reported the clause absent, so
  `scripts/check-template-conformance.sh` failed T1 and never evaluated
  T2–T4. This came from the mint, not from this milestone: `main` carries the
  same defect, and `build/just/repo-init.just` emits the correct `)))`.
* Toolchain pins: the Zig download in `zig-ci.yml` and in the container's
  `toolchain` stage now forces HTTPS and a minimum of TLS 1.2
  (`curl --proto '=https' --tlsv1.2`), so a pinned SHA-256 cannot be
  satisfied by a downgraded transfer.
* Toolchain pin: Zig 0.16.0 → 0.17.0 (`mise.lock`).
* `src/interface/`: the template's example ABI/FFI seam is replaced by the
  zig-dnssec C ABI; its separate `ffi/build.zig` is gone (the root
  `build.zig` builds and tests the seam).

=== Inherited from rsr-template-repo at mint (2026-10-13)

The entries below describe the template this repository was minted from, not
zig-dnssec itself.

==== Template [Unreleased]

==== Added

* `www/` site-operations bundle (issue #53): canonical `.well-known/`
  metadata, publishable content, policy sources, error bodies,
  security-header templates, Caddy/nginx/Apache integration examples, an
  authoritative-only BIND 9 starting hand with record templates,
  encrypted-DNS/privacy and TLS guidance, explicit opt-in profiles,
  schemas, planted-control tests and operational runbooks.
* `scripts/migrate-wellknown-to-www.sh` — conflict-safe migration of a
  repository-root `.well-known/` into `www/.well-known/` (identical copies
  de-duplicated, root-only content moved, divergent content quarantined —
  see Changed).
* `scripts/sweep-wellknown.sh` — stage 5 (#119) batch driver: classify,
  migrate, test and commit across the estate in batches of 25, holding
  Pages-served and non-RSR repositories for a human decision instead of
  sweeping them blind.
* `www/runbooks/stage5-wellknown-sweep.adoc` — how to run the sweep, and
  how to recover from a quarantine.
* Mint wiring for the `www/` bundle: `repo-init` now invokes
  `scripts/migrate-wellknown-to-www.sh` when the tree being minted still
  carries a legacy root `.well-known/`, and runs `www/tests/run-all.sh`
  afterwards. Both are no-ops for a repository minted from the current
  template; they exist for running `repo-init` over a tree that predates
  #53. #106 described both as already present — neither was, which is a
  fair part of why the estate still carries root `.well-known/` directories.
* `scripts/merge-actions-lock.rs` — merges an archetype's lock fragment
  (`archetypes/<name>/actions.lock`) into the spine's
  `.github/workflows/actions.lock` at mint. A record that differs between
  the two stops the mint. `tests/workflows/archetype_lock_merge_test.sh`
  (wired into estate-rules) checks the merged lock with
  `check-lock-sync.sh`, and checks that the old clobber, a missing record
  and a conflicting record all fail.

==== Changed

* Canonical `.well-known/` location moved from the repository root to
  `www/.well-known/`. Well-known enforcement, Groove checks, the root-shape
  allowlist, the SSG bootstrap and the documentation now prefer the `www/`
  location and accept the legacy root location with a warning during the
  migration window.

==== Changed

* Divergent root/`www/` `.well-known/` content is now quarantined to
  `www/.legacy-well-known-<YYYYMMDD>/` instead of being left in place: the
  estate-wide sweep (#119) is unattended, so a conflict must not halt it, and
  must not be silent either. The `www/` copy is untouched, both hashes are
  printed, and the run exits non-zero. `--in-place` keeps the previous
  contract (preserve both, exit 1) for hand resolution. The quarantine lives
  under `www/` rather than at the root because the root allowlist is matched
  literally and bidirectionally, so a dated root directory would report as
  drift in every repository swept.

==== Fixed

* Julia mints start with Lock Sync green. The julia-library overlay
  shipped its own `actions.lock`, which replaced the spine's at mint, so
  every spine workflow lost its records. The records now ship beside the
  overlay and are merged in. The overlay workflows gain SPDX headers and
  top-level permissions, and julia-docs builds with plain steps instead of
  the allowlist-refused julia-buildpkg/julia-docdeploy. julia-actions/cache
  moves to v3.5.0. The root allowlist admits `?Project.toml` and `?test/`.
  The docs checkout sets `persist-credentials: false`, so package code run
  while the docs environment is set up finds no stored token. deploydocs
  still receives GITHUB_TOKEN.
* `just repo-init julia-library` accepts a `<Name>.jl` slug. The PROJECT
  tokens map its dot to an underscore, and the default service name is the
  slug in lower case.

* Dev container starts for everyone: dropped the ghcr.io dev container
  features (anonymous pulls returned 403), installing just from Wolfi and a
  SHA-256-checked Nickel 1.17.0 binary instead. The default
  `.devcontainer/devcontainer.json` now targets rootless Podman
  (`--userns=keep-id:uid=65532,gid=65532`, `label=disable`) so the workspace
  is writable as wolfi-base's built-in `nonroot`; Docker, Codespaces and
  Gitpod use `.devcontainer/docker/devcontainer.json`.
* `dot-wellknown-enforcement.yml` now drives the migrator that #106 described
  but never wired up: previously the workflow only printed advice to run it,
  so nothing verified that a repository would survive the migration. It now
  runs the migrator in `--dry-run` and turns every conflict into a
  `::warning` annotation — a warning, not an error, for the migration window.
* The migrator's acceptance test had encoded the in-place contract as the
  required behaviour, contradicting #106's stated design; it now proves the
  quarantine contract across nine scenarios, including the collision case
  where a quarantine name is already taken.
* `tests/e2e/template_instantiation_test.sh` fed the three container answers
  only when `container/` existed, but `build/just/repo-init.just` asks those
  questions when `build/container/` does. On any complete checkout — which is
  what CI clones — the recipe asked three questions the test had no answers
  for, `read` hit EOF, and the recipe exited 1, so the instantiation e2e was
  red at the container prompt. The guard now matches the recipe's own path.
  (The test also needed `ruby` for the two mint tools. Those are Rust as
    of 2026-09-18, so it no longer stops there.)

* Restore the modular `just` recipes removed by the root-layout refactor, so
  `just repo-init`, validation, assessment, container, Groove, and proof tasks
  are available again.
* Require lowercase hyphenated repository slugs at initialization and verify
  that both Guix package definitions receive the rendered slug and project URL.
* Keep template validation aligned with authority documents moved under
  `docs/`, and repair the cross-platform `cloak`/`uncloak` recipe syntax.
* Restore the tracked-file language-ban gate with regression fixtures proving
  that supported Zig passes while prohibited V-language remnants fail.
